Role & permission model

Permissions are the real unit. A role is just a named, reusable bundle of them — which is what makes a custom role possible without new code.

RoleBranch scopeCore access
SuperadminAll branchesEverything, including staff management, custom roles, system settings, and the full audit log.
Branch ManagerAssigned branch onlyFull operational access to their branch — inventory, orders, staff schedule, branch-level financials and promotions within superadmin-set limits.
PharmacistAssigned branch, or all (configurable)Prescription review queue, pharmacy catalogue, pharmacist chat. No vet, no supermarket, no financials, no staff management.
Veterinary StaffFlagship only (the only branch with a clinic)Appointment calendar, pet profiles, vet product catalogue, post-visit medical records. No pharmacy prescriptions, no supermarket inventory.
Inventory ManagerAssigned branch onlyFull CRUD on their branch's stock, stock transfer requests. No financial or sales reports.
Cashier / FulfillmentAssigned branch onlyView and advance order status. No price/discount edits, no visibility into other staff's performance.
Customer Service RepAll branchesSupport tickets, read-only order lookup, refunds up to a configured cap, customer communication history.
Delivery CoordinatorAll branches (or assigned, per business need)Delivery queue, rider assignment, third-party dispatch, delivery exception handling.

Branch scope is a modifier, not a flag per branch. The brief's example names can_access_branch_X_only — written that way, every new branch needs a new flag. Instead, each role assignment carries one scope value: all_branches or assigned_branch, alongside which specific branch(es) that assignment covers. Adding a 4th branch (technical architecture doc, §08) touches zero permission-flag definitions.

How a permission check actually runs

At request time

  • The API Gateway's RBAC guard (technical architecture doc, §01) checks the caller's role_assignments for the specific flag the endpoint requires, plus branch scope if the resource is branch-owned.
  • A denied request is logged, not just silently rejected — a pattern of denied attempts is itself a signal worth seeing.

Immediately on change

  • Permission edits invalidate that staff member's cached permission set right away — enforced via a short-TTL Redis-cached permission snapshot per session, re-checked on next request, not a stale JWT claim trusted until it expires.
  • A role change mid-shift (e.g. a cashier promoted to branch manager) takes effect on their very next action, not at next login.

Order detail (not pictured) opens as a side panel: itemised lines, customer info, delivery tracking map, status buttons matching the order's actual next valid states only (no skipping from Confirmed straight to Delivered), and an internal notes field visible to staff only, never the customer.

Product catalogue

Per-product editor

  • Core fields plus a per-branch override table: same SKU, different stock and price per branch, inline-editable.
  • Prescription-required toggle (and, per the compliance doc, a third Controlled state) directly on this screen — classification lives where the product itself is edited.
  • Image upload with drag-reorder for the gallery.
  • Low-stock threshold, configurable per product, defaulting to a category-level setting.

Bulk upload

  • CSV/Excel template download with the exact column headers the importer expects.
  • Upload runs a dry-run validation pass first — shows row-level errors (bad category, missing price) before committing anything.
  • Category management: nested tree with drag-to-reorder, mirroring the storefront's category structure from the IA spec.

Inventory & stock

Per-branch stock dashboard

  • Table of every SKU at the viewer's branch(es), stock level, threshold, and a visual low/critical indicator.

Stock transfers

  • Sending branch requests, receiving branch confirms before stock moves in the system — matches the brief's two-sided approval exactly.

Expiry tracking pharmacy-critical

  • Automated 90/60/30-day banners on the inventory dashboard, plus a dedicated "Expiring soon" filter view.
  • Write-offs for expired stock require a reason code and, above a configurable value threshold, manager approval.

The per-line approve/query/reject screen, the reviewing-pharmacist and Superintendent Pharmacist auto-attachment, and the append-only prescription_audit trail are all specified in the compliance doc's §02 wireframe — reused here unchanged. 06

Customers & promotions

One customer record pulling together every vertical they've touched; promotions that a non-developer can actually ship.

Customer profile

At a glance

  • Name, contact, join date, lifetime value, loyalty points balance.
  • Saved addresses, payment methods on file (tokens only — technical architecture doc §07).

Cross-vertical history, one scroll

  • Order history across all three verticals, not three separate tabs.
  • Prescription request history, linking into the compliance queue's own record.
  • Pet profiles, each expandable to its visit history.
  • Support ticket history and manual account actions: suspend, add store credit, add an internal note.

Promotions & combo deals

Promo codes

  • Percentage or fixed, minimum spend, usage limit, date range, applicable products/categories — matches the Order calculation engine's promo step exactly (technical architecture doc §04).

Combo/bundle deals

  • Pick 2+ products, set a bundle price or a discount — feeds the calculation engine's combo-discount step, applied before any promo code.

Homepage banner scheduling

  • A superadmin or branch manager edits the "Baby Care Combo — Save 15%" banner (homepage spec §07) directly — headline, end-time for the countdown, and the linked combo — with no developer involvement, exactly as the brief specifies.
07

Delivery & financial reports

Where the courier abstraction from the technical architecture doc becomes a screen, and where the money gets reconciled.

Delivery management

Active deliveries

  • List/map toggle of every in-flight delivery, filterable by branch and provider.
  • Assign to an in-house rider or trigger a third-party courier's createDelivery() call (technical architecture doc §05) from the same screen — the staff member doesn't need to know which provider is behind the button.
  • Exceptions (failed delivery, address issue) surface as a distinct status, routed to Customer Service.

Provider performance & fee rules

  • On-time rate and average cost per provider, side by side — the data that justifies which provider gets offered first at checkout.
  • Delivery fee tiers by distance, configurable per branch, feeding the calculation engine directly (technical architecture doc §04).

Payments & financial reports

Transaction log

  • Synced with Paystack via the webhook (technical architecture doc §03/§05) — a reconciliation view flags any order marked paid locally with no matching Paystack reference, or vice versa.
  • Refund log, each entry showing who issued it and against which limit (the Customer Service ₦10,000 cap, or a superadmin override).

Revenue reports

  • Filterable by branch, vertical, date range, payment method — same filter chip pattern as every other table in this product.
  • CSV/PDF export for the business's accounting process.

Staff directory

Directory & accounts

  • Searchable list: name, role, branch, status (active/suspended), last login.
  • Add/edit/deactivate — deactivation is immediate per the §00 session-revalidation rule, not "effective next login."

Audit & schedule

  • Per-staff activity log: logins, and every write action they took, each linking to the record it changed.
  • Basic shift/schedule entry, primarily to feed vet staff availability (compliance doc §06) rather than a full workforce-management tool.

Who can touch the role builder. Only create_custom_roles — Superadmin by default — reaches this screen. A Branch Manager's Staff & roles view lets them add/deactivate staff at their own branch and assign existing roles, but never define a new one or edit what a role's permissions are.

Analytics & system settings

Insight for everyone with reporting access; configuration for the superadmin alone.

Analytics & insights

Best-sellers

  • Per branch and per vertical.

Retention

  • Repeat-purchase rate, cohort view.

Cart abandonment

  • Carts created vs. orders placed, by vertical.

Peak-time heatmap

  • Paystack keys and webhook configuration.

Content

  • Terms of Service / Privacy Policy content.

Assumptions & open items

Calls made to keep this spec concrete, plus items tied to decisions in the earlier documents.

  1. Refund cap defaultsThe ₦10,000 Customer Service cap and the Branch Manager's "branch cap" are sample figures. Needs real numbers from finance, and whether the cap is a single-transaction limit or a rolling daily/monthly one.
  2. Pharmacist branch scope default§00 lists Pharmacist as "assigned branch, or all (configurable)" — confirm whether prescription review is centralised (any pharmacist, any branch's queue) or branch-siloed by default; this affects queue-routing logic, not just the permission flag.
  3. Branch Manager's promotion limits"Within superadmin-set limits" needs the actual limit shape — a discount percentage ceiling, a max combo count, or both.
  4. Stock write-off approval threshold§04 references a configurable value threshold above which a manager must approve — needs a real ₦ figure from the business.
  5. Delivery Coordinator's branch scopeModelled as all-branches by default in §00 since delivery often crosses branch boundaries at the dispatch level — confirm whether the business actually wants branch-siloed coordinators instead.
  6. Session-revalidation mechanism§00 specifies immediate effect on permission change via a short-TTL cached permission snapshot — needs a concrete TTL value from engineering (seconds, not minutes, if "immediately" is to be taken literally).
