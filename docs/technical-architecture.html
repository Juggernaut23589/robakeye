00

Stack & decisions

The brief offers real choices at several layers. These are the calls, made for a 3-branch MVP serving customers on mobile data in Ibadan — not for a hypothetical platform at 10x the scale.

Backend API shape
REST, versioned (/v1)Not a REST+GraphQL hybrid, and not tRPC. The API has to serve the Next.js web app, the admin backend, future mobile apps, and inbound webhooks from Paystack/couriers/WhatsApp — tRPC's whole-stack type-sharing only pays off when every consumer is the same TypeScript codebase, which webhooks and a future native app never are. GraphQL is deferred — see the catalogue note below.
Backend framework
NestJS over LaravelOne language (TypeScript) across frontend and backend halves the context-switching for a small team, and NestJS's module system maps directly onto the Pharmacy / Vet / Supermarket / Order / Payment / Admin boundaries the brief already names.
Catalogue search
Postgres full-text + trigram for MVP; Algolia when catalogue size justifies itThree branches' worth of SKUs doesn't need a dedicated search cluster on day one. pg_trgm gives typo-tolerant search against the same database, no new infra. Revisit Algolia/Elasticsearch once product count or query volume makes Postgres search slow — the schema doesn't need to change either way.
Hosting (MVP)
Vercel (frontend) + Railway (API + Postgres + Redis)Both scale by upgrading a plan, not by re-architecting — appropriate for pre-revenue traffic. A move to full AWS (EC2/RDS/S3/CloudFront) is a planned migration, not a rebuild, once volume or a specific compliance need (e.g. data residency) forces it.
Real-time
Socket.io, scoped to 3 use cases onlyOrder status, delivery tracking, and the pharmacist live-chat fallback. Not a general pub/sub layer — everything else (cart, catalogue) stays request/response with Redis caching.
Monolith vs. microservices
Modular monolith, one deploy unitNestJS modules give the boundaries; the database gives the schemas per module. Splitting a module into its own service later is a redeploy of that module behind the same API contract, not a rewrite — see section 08.

Entity detail fields the brief's shorthand needs spelled out

EntityKey fields beyond the brief's listWhy
branch_inventorySeparate table, not a JSON column on products: (product_id, branch_id, stock_qty, price, updated_at), unique on (product_id, branch_id).The IA spec's location-aware logic reads and writes this constantly — a relational table with a unique constraint lets Postgres enforce "one stock row per product per branch" and makes the race-condition-safe decrement in section 04 a single UPDATE … WHERE stock_qty >= qty statement.
prescription_auditAppend-only: (prescription_id, event, actor_staff_id, licence_number, timestamp, metadata). No UPDATE or DELETE grant on this table for any application role.Matches the IA spec's compliance note — the audit trail a regulator asks for has to be structurally un-editable, not just conventionally append-only.
role_assignmentsJoin table between staff and roles_permissions, not a single role enum column on staff.A branch manager who also fills in as a cashier needs two roles at once — the brief's permission list ("approve_prescriptions", "manage_staff" etc.) implies roles aren't mutually exclusive.
orders vs. sub-ordersorders stores the customer-facing total and payment; a nullable parent_order_id self-reference lets a split-fulfilment cart (IA spec, section 05) become 2+ child order rows sharing one payments row.Keeps "one payment, two deliveries" relational instead of overloading order_items.branch_id alone to imply a split that the status/tracking UI also needs to reason about independently.
addressesSeparate table, not an array column: (user_id, label, line1, area, lat, lng, is_default).Geocoded once on save, not re-geocoded on every checkout — the Distance Matrix calls in section 04 read stored coordinates.
delivery_partners.api_credentialsEncrypted at the application layer (not relying on column-level DB encryption alone) with keys in a secrets manager, never in the row's plaintext reach of a routine DB backup.

04

Core business logic

The two functions everything else in the platform calls — implemented, not just described, since a pseudocode gap here is where real bugs live.

Location-aware branch matching

async function findAvailableBranches(customerCoords, productId) {
  // 1. One query joins branch_inventory → branches, no N+1 per-branch lookup
  const rows = await db.query(`
    SELECT b.*, bi.stock_qty, bi.price,
           earth_distance(ll_to_earth($1,$2), ll_to_earth(b.lat,b.lng)) / 1000 AS distance_km
    FROM branches b
    JOIN branch_inventory bi ON bi.branch_id = b.id
    WHERE bi.product_id = $3
    ORDER BY distance_km ASC
  `, [customerCoords.lat, customerCoords.lng, productId]);

  const inStock = rows.filter(r => r.stock_qty > 0);
  const inRadius = inStock.filter(r => r.distance_km <= r.delivery_radius_km);

  if (inRadius.length) {
    return { status: 'matched', primary: inRadius[0], alternatives: inRadius.slice(1) };
  }
  if (inStock.length) {
    // outside every branch's normal radius but still gettable — IA spec §02 step 4
    return { status: 'outside_radius', branch: inStock[0], feeMultiplier: 1.6 };
  }
  return { status: 'unavailable' }; // triggers the notify-me waitlist write
}

Race condition. This function only reads stock. The actual decrement happens at POST /v1/cart/items and again at order creation, as UPDATE branch_inventory SET stock_qty = stock_qty - $1 WHERE product_id=$2 AND branch_id=$3 AND stock_qty >= $1 — a single atomic statement, so two customers racing for the last unit can't both succeed, matching the IA spec's explicit rule in §02.

Order calculation engine

async function calculateOrderTotal(cart, promoCode, customer, deliveryMethod) {
  // Fixed order — see IA spec §05 for the customer-facing version of this waterfall
  const itemsSubtotal = sum(cart.items.map(i => i.unitPrice * i.qty));
  const comboDiscount  = await applyComboRules(cart.items);              // step 2
  const promoDiscount  = await validatePromo(promoCode, itemsSubtotal, cart);  // step 3
  const loyaltyDiscount = applyLoyaltyPoints(customer.pointsToRedeem);        // step 4

  const subtotal = itemsSubtotal - comboDiscount - promoDiscount - loyaltyDiscount;

  // Split by fulfilling branch — one fee per sub-order, not one fee for the cart
  const subOrders = groupByBranch(cart.items);
  const deliveryFees = await Promise.all(
    subOrders.map(so => calculateDeliveryFee(deliveryMethod, customer.address, so.branch))
  );
  const deliveryFee = sum(deliveryFees);

  const serviceCharge = getServiceCharge(cart.orderType);   // e.g. vet booking fee
  const tax = applyTax(subtotal, cart.items);          // per-category VAT code, see §07
  const finalTotal = subtotal + deliveryFee + serviceCharge + tax;

  return {
    itemsSubtotal, comboDiscount, promoDiscount, loyaltyDiscount, subtotal,
    subOrders: subOrders.map((so, i) => ({ ...so, deliveryFee: deliveryFees[i] })),
    deliveryFee, serviceCharge, tax, finalTotal
  };
}

Server is the source of truth. POST /v1/cart/quote runs this exact function and the client renders its response — the frontend never recomputes totals locally for anything but an optimistic UI preview. POST /v1/orders runs it again at order creation and persists the result; a price shown at review that doesn't match what's charged is treated as a bug, not a display nuance.

Security & compliance

What's non-negotiable before launch, mapped to where it's actually enforced.

RequirementEnforced at
HTTPS everywherePlatform-level (Vercel/Railway terminate TLS); HSTS header set on every response.
Rate limitingAPI Gateway module, Redis-backed, per-IP and per-account; tighter limits on /v1/auth/* and /v1/prescriptions/*.
Input validationZod schemas on every endpoint, shared between frontend form validation (React Hook Form + Zod) and backend — one schema, not two that can drift.
Encryption at restPrescription uploads and PII: S3 server-side encryption plus application-layer encryption for delivery_partners.api_credentials. Database-level encryption on the RDS/Railway volume as a second layer, not a substitute for the first.
NDPA 2023 complianceData minimisation on every schema (don't collect what isn't used), a documented data retention policy per entity (prescriptions longest, per PCN guidance — IA spec §03/§08), and a subject-access-request process for the admin module.
PCI-DSS scopeMinimised entirely — Paystack Inline/Popup means card data never reaches Robakeye's servers; only a token and a reference are stored.
2FA for admin/superadminMandatory at login for any staff role above cashier — TOTP, enforced in the Admin module's auth guard, not optional per-user.
Audit logsprescription_audit (append-only, §02) plus a general admin_audit_log for inventory edits, staff changes, and refunds — every write from an admin route logs actor, action, and timestamp automatically via a NestJS interceptor, not manually per-endpoint.
BackupsDaily automated, 30-day retention minimum, tested restore quarterly — an untested backup is not a backup.
08

Scalability

What adding a 4th branch, a new vertical, or real traffic actually touches.

Adding a branch

  • One INSERT into branches plus its branch_inventory rows — no schema change.
  • Branch-matching (§04) already ranks over all branches; a 4th branch is just another row it sorts.
  • Admin module's per-branch dashboard and RBAC scoping already key off branch_id, not a hardcoded count.

Adding a vertical

  • categories.vertical is already an open string, not an enum of exactly 3 — a 4th vertical is new category rows plus (if it needs one) a new NestJS module behind the same Catalogue service.
  • The product/order schema doesn't assume 3 verticals anywhere; only UI-level copy ("Pharmacy · Veterinary · Supermarket") does.

Splitting the monolith

  • Each NestJS module already owns its own schema tables and talks to others through defined services, not raw queries — the seam to extract a module into its own deployable service is the module boundary itself.
  • Split only when a specific module's load or deploy cadence genuinely diverges from the rest — not preemptively.

The brief's instinct to stay a modular monolith for MVP is the right one for this traffic profile. The cost of over-engineering into microservices early (network calls where function calls used to be, distributed transactions for what's currently one Postgres transaction) is larger than the cost of a later, deliberate split once a real bottleneck names itself.

Assumptions & open items

Technical calls made to keep this architecture concrete, plus items that depend on decisions from the earlier specs.

  1. Tax engine§04's applyTax assumes per-category VAT codes exist, same open item as the IA spec §08 — needs the real category→tax-code mapping before the Order module's tax logic can be finalised.
  2. Prescription retention period§07 defers to "PCN guidance" for how long prescription_audit rows and uploaded images must be kept — needs a confirmed number of years before the S3 lifecycle policy can be set.
  3. Delivery radius & fee formula§04's feeMultiplier: 1.6 for out-of-radius delivery is a placeholder constant — needs real per-branch radius values and a fee formula from the business (same open item as IA spec §08).
  4. Search engine trigger§00 defers Algolia/Elasticsearch until catalogue size or query volume justifies it — needs an agreed threshold (e.g. SKU count or P95 query latency) so the migration isn't decided reactively under load.
  5. Mobile appThe brief's eventual app-store badges (homepage spec §08) aren't reflected in this architecture — if a native app is actually planned, the REST API's versioning and auth (refresh-token rotation, not just session cookies) needs confirming as mobile-ready now rather than retrofitted later.
  6. Split-order payment reconciliation§02's parent_order_id model needs a concrete refund/cancellation procedure when only one sub-order fails after a single combined payment — same open item flagged in the IA spec §08, now also a Payment-module design question.
